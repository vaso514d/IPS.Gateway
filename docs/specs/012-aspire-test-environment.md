# Specification 012: Aspire test environment (SQL Server, API and simulators in containers)

Status: specification on codex/payment-initiation, stacked on 011 (651c1ab) and the earlier unmerged slices 005a-005d, 007a-007c, 008a-008c, 009 and 010. The owner asked on 2026-10-07 for an Aspire starter that tests can use and that runs in containers, and chose: AppHost, SQL container, API and tests; the simulators as a test-support project that is never shipped; measured performance moves to 013 on top of this stack. The owner approved the specification on 2026-10-07; implemented and reviewed ([review evidence](../reviews/012-aspire-test-environment.md)), and the owner approved the commit on 2026-10-07.

## Scope

A reproducible environment that starts the whole service the way a deployment would, without LocalDB or in-process hosts, and that tests can drive:

- an **Aspire AppHost** under `tests/` that declares a SQL Server container, the middleware API (as a project for the inner loop, and as a container built from a Dockerfile) with any number of replicas, and a simulator service standing in for IPS, the CBS and the Proxy Solution;
- the **simulators** as a test-support project that is not part of the deployable service (an explicit, owner-approved exception to the rebuild plan's "no standalone mock hosts"), with a small control API so a test can set behaviour and read what was received;
- **tests** that start the stack through `Aspire.Hosting.Testing`, prove it end to end and re-run the multi-instance proof of 011 against real containers;
- a short guide for running it locally (`docs/local-environment.md`).

Not in scope: replacing LocalDB in the existing tests (they keep running as today), the incoming receive path in the simulator beyond what the proof needs (it is a clean extension point, listed in the limits), load scenarios and numbers (013), production deployment, orchestration manifests, observability backends, authentication or any change to the service's behaviour. The Dockerfile packages the existing API; it adds no endpoint or code to it.

## Design

- **Projects (all under tests/, outside the shipped solution layers).** `IPS.Middleware.AppHost` (Aspire AppHost SDK project), `IPS.Middleware.Simulators` (a minimal ASP.NET Core host) and `IPS.Middleware.AspireTests` (xUnit, Aspire testing). The AppHost references the API and the simulators as project resources; versions of the Aspire packages are pinned in `Directory.Packages.props`. The architecture tests are extended so these projects cannot be referenced by `src/`.
- **AppHost.** A SQL Server container with a generated password and a database `Middleware`; migrations are applied once the database is ready, by the same EF migrations the service ships (the service still never migrates at startup); the simulators; the API with `Payments:Outgoing:*`, `Proxy`, `ConnectionStrings:Middleware` and the signature-trust settings injected as environment variables from the other resources, `WaitFor` the database and the simulators, replicas settable (`WithReplicas`), health probes on `/health/ready` and `/health/live`. With `Middleware:Container=true` the API instances are the same service run as containers from `src/IPS.Middleware.Api/Dockerfile`. No secret is stored in the repository.
- **Simulators.** One process with three route groups: IPS (`POST /Message` answered ACCP/RJCT or pacs.002 per configured behaviour, signed with a development key whose certificate the AppHost passes to the API as the IPS signature trust; possible-duplicate header recorded), the CBS callback (`POST /api/ips/transactions/status/receive`, recorded), and the Proxy Solution (`POST /PRX/register|update|remove`). A control API (`/_sim/...`) sets behaviour (reject, lose reply, delay, block until released) and returns what was received (messages, flags, versions, callbacks, proxy calls). The simulators reuse the message shapes of the existing test simulators; replies are signed with the service's own signer instead of Java, so the container needs no JDK (the independent Java verification stays in the existing signing tests).
- **Tests.** A shared fixture starts the distributed application once per test class collection and exposes the API's and the simulator's HTTP clients. Tests need Docker; when Docker is not available they are skipped with an explicit reason rather than failing the whole run, and the skip count is reported.
- **Dockerfile and image.** A runtime-only image on the ASP.NET 10 image, non-root user, port from `ASPNETCORE_HTTP_PORTS`, no configuration baked in (everything is environment); its build context is the output of `dotnet publish`, which the AppHost produces on the host. No change to `src/` code.

## Acceptance

- `dotnet build` of the solution builds the three new projects with no warnings; format and EF model checks are unchanged; the existing suites pass unchanged.
- With Docker running, the Aspire tests pass three times in a row: the stack reaches ready (SQL, simulators, API healthy); `/health/ready` is 200; a pain.002 and a pacs.008 send return the final status and the CBS callback arrives once; a rejecting IPS ends Rejected; a lost reply is recovered by one flagged resend of the same bytes; a proxy register returns the Proxy's accept and a reject; invalid input is a 400; and with two API replicas 40 payments are each sent once and reported once with both replicas having sent part of the work (the 011 proof against containers).
- The same stack runs with the API as a container built from the Dockerfile (a smoke test: ready, one send, one callback), and a local run with `dotnet run --project tests/IPS.Middleware.AppHost` shows the dashboard and the three resources.
- Without Docker the Aspire tests are skipped with the reason and the rest of the suite is green.
- Independent Standards and Spec reviews; `docs/local-environment.md`, `docs/architecture.md` and the ledger updated.

## Limits and risks

The environment proves behaviour against simulators, not against a real IPS, CBS or Proxy Solution. Container startup makes these tests slower than the in-process ones (tens of seconds for the first test), and they depend on Docker and the SQL Server image being pullable. The simulators' fidelity is only what the existing test simulators had. The incoming receive path (the IPS long poll, acknowledgement, core submissions) is not simulated in this slice and is the first extension. Aspire is a new test-time dependency set (AppHost SDK, hosting and testing packages); none is referenced by the shipped service.

## Implementation notes

- Aspire 13.6.1 (AppHost SDK, SQL Server hosting, testing) is pinned in `Directory.Packages.props` and referenced only by the AppHost and its tests. The existing dependency test already fixes the exact project references of every `src/` project, so none of them can reference the new projects.
- The Dockerfile is runtime-only and the AppHost publishes the API on the host first. A multi-stage build restoring inside the container failed on this machine because the network's TLS inspection is untrusted inside containers (NU1301 UntrustedRoot); publishing on the host avoids needing NuGet access in the image and also makes the build faster.
- A container reaches the simulators on the host as `aspire.dev.internal`, so that name is a SAN of the generated server certificate, which the service trusts by file; revocation checking is off for these loopback-style endpoints and the service runs in Development without mutual TLS and with unsigned messages allowed (the simulated IPS does not check the service's signature; the service's signing is covered by the existing tests).
- The simulators have a plain HTTP endpoint for the health check and the control API and a TLS endpoint for what the service calls, because Aspire's health probe cannot trust the generated certificate.
- The simulated IPS signs its answers with the service's own signer, so the container needs no JDK; the independent Java verification stays in the existing signing tests.
- The two-instance proof identifies instances by the protocol version header (`1`, `2`) and leaves work waiting by limiting each instance's admission to 4, so both instances' recovery sweeps claim it.
- Docker Desktop was not running when the work started; it was started on the developer machine.
- The Aspire work found a defect in 010 that the in-process tests could not: a stall bound of three times a 200 millisecond sweep interval turned a briefly busy container Unhealthy. The one change to `src/` in this slice is therefore the readiness stall rule: a loop is stalled after `WorkerStallFactor` times its period plus `Diagnostics:WorkerPassAllowance` (default 10 seconds), recorded in the 010 spec and `docs/configuration.md` and covered by a test. A hung loop with a short period is now noticed after roughly the allowance, which is the intended trade-off.
- The simulators duplicate part of the in-process simulators of the integration tests (reply shapes, lose/reject behaviour). They are separate because they must run as a process in a container and sign with the service's own signer; sharing the builders would make the integration tests depend on a hosted project. The duplication is accepted and recorded here.
- The generated certificates and passwords live in a temporary directory for the run (only the public parts are mounted into a container) and are deleted when the AppHost stops; the passwords are visible in the dashboard and the container environment, which is acceptable for throwaway files. The container image is for local and test runs: it is configured as Development by the AppHost.
- The migration runs when the database is ready and `WaitFor` does not wait for it, so the API may start first; its readiness check (migrations current) and the tests' wait for health hide that order. A scenario that needs a migrated database before the first request waits for health.
