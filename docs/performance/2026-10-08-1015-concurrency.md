- **Where 8 and 16 lose time.** Both queue: the 50 per second need about 15 payments in flight at the median of 0.28 s, and more in bursts. At 8, payments that waited for admission longer than the 20-second submission window were reported NotSent (253) and their requests answered 504 after the 30-second HTTP wait. At 16 the queue formed in the first measured minute (that minute's settlement p95 was 9.9 s, the next two 519 and 456 ms) and drained without a missed deadline.
- **32 does not queue.** At most 49 requests were open against 64 slots.
- **The SQL pool.** The peak of SQL sessions per API process stayed at 40 or below, so it stays within Max Pool Size 100. Queueing raised it at 16, because waiting requests read their status.
- **Outbound connections.** An instance makes at most `Concurrency` concurrent IPS calls, since investigations and resends run inside the same slots. Startup requires `Concurrency <= Payments:Outgoing:Transport:Ips:ConnectionLimit` (100). Callbacks use `CallbackConcurrency` (8) against the CBS `ConnectionLimit` (100). Neither limit has to grow with 32.
- **A statement that scanned at 32.** In the 32 run the preparation read of the ready message (`OutgoingMessages` by payment, direction 0, initial exchange) ran as a clustered index scan:
  - 9,639 logical reads and a 35.6 ms mean per execution, 342 s of SQL time over the run;
  - in the 8 and 16 runs it was cheap.

  The targets still passed. The first 10-minute baseline then showed the cause: the row goal of the `TOP(2)` that `SingleOrDefault` generates makes SQL Server scan the growing journal. The journal is now read without `TOP` (013a implementation notes, correction 3).

## Recommendation

Ship `Payments:Outgoing:Execution:Concurrency` 32. It meets every target where 8 and 16 queue. It is not worse than 16 on any target, and it stays within the SQL pool and both connection limits with room to spare. Per the owner's decision of 2026-10-08 (32 if feasible), `src/IPS.Middleware.Api/appsettings.json` now ships 32. No coupled limit changes. The default is per instance, and results are indicative of one machine (013 risks).
