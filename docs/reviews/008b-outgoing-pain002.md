# Review 008b: outgoing pain.002 (refusal of a payment initiation)

Branch codex/payment-initiation, stacked on 008a (29a38ca) and the unmerged slices 005a-005d and 007a-007c; no merge is approved. On 2026-10-07 the owner approved the four decisions and the [specification](../specs/008b-outgoing-pain002.md). Commit and merge approval are pending.

## Delivered

- **Intake.** `Pain002Request`, `Pain002Validator`, `ValidatedPain002`, `AcceptedPain002` and `Pain002Intake` on the shared outgoing core. The message id is the caller's `Id` and also the stored transaction id; it must be unused, and the unique indexes fence a race. The initiation's payment information id is the status reference.
- **XML and signing.** `pain.002.001.14` (`CstmrPmtStsRpt`) in the IPS v1 profile, validated against the embedded schema (added) and signed like the other types. `OrgnlMsgNmId` is `pain.001.001.12`.
- **IPS's answer.** `IpsReplyInterpreter.Interpret(response, sent)` hands a pain.002 correlation to `Pain002ReplyInterpreter`: header `X-MONTRAN-IPS-ReqSts` `ACCP` is Accepted, `RJCT/<code>` is Rejected with IPS's code, anything else is Unresolved and resent. The body is neither required nor verified. Deviation from the design sketch: the dispatcher lives inside `IpsReplyInterpreter` instead of a separate composite, so no call site or existing test changed.
- **API and recovery.** `POST /api/ips/pain002/send` returns 200 or 504 (duplicates return the current status at once); recovery is the shared possible-duplicate resend; no pre-send deadline.
- **Persistence.** Snapshot JSON by message type; the three check constraints widened in every occurrence; one additive migration `OutgoingPain002` generated by the EF CLI (no pending model changes).
- **Contracts metadata.** `SendPain002Async` success code 202 to 200 with a new description; `public-api.json` edited explicitly for that one method; exception recorded in the baselines README.

## New tests

- **Unit:** validation (every rule, normalization, UTC conversion).
- **Processing (real SQL, Java-verified signature):** the exact message sent, optional originator name and additional information, ACCP, `RJCT/1017`, `RJCT/1009`, bare `RJCT`, the header deciding over a contradicting body, PDNG/empty/missing/503/500 and conflicting headers unresolved, duplicate client reference, reused id, concurrent id race, a crash at each checkpoint, snapshot round trip.
- **Recovery:** flagged resend of the original bytes, rejecting header on the resend is final, backoff and resend, window end.
- **Host and process kills:** 200, 400, rejected, 504 plus duplicate, lost-reply recovery with identical bytes; killed process at ready, marker, response and resend-response.
